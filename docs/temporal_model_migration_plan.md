# Temporal lifecycle migration: Phase 1 audit and impact report

Status: Phase 1 audited 2026-10-03; Phase 2 approved and implemented as archive fingerprinting, protection tests and a separate raw metadata index. The next implemented layer adds dated active baseline semantics, deployment observations and provider-scoped deployments. Identity resolution and lifecycle events remain proposals. See `docs/temporal_archive_phase2.md` and `docs/temporal_deployment_layer.md` for implemented contracts and preservation results.

## Repository and archive inventory

The daily collector (`python -m collector`) writes one UTC day directory under `data/raw/YYYY-MM-DD/`. `collector/run.py` invokes seven legs; `collector/paths.py` fixes their names; `collector/manifest.py` holds manifest schema version 1 and leg status. `collector/storage.py` gzip-compresses the received bytes deterministically and atomically replaces output files. A completed day is a no-op on rerun; a partial day can be resumed, so files and its manifest **can be rewritten while partial**. The current GitHub workflow runs at 06:20, 12:20, 18:20 and 23:40 UTC, commits `data/raw`, then audits it. CI runs Ruff and pytest but ignores raw-only pushes. `scripts/pull_snapshots.ps1` pulls and audits the local copy. Git remains the chosen Bronze store under ADR 0001; S3 is only a future decision.

As inspected locally, `data/raw` has 36 day directories (2026-08-28 through 2026-10-02), 36 `_manifest.json` files and 181 compressed payloads, totaling 217 files / 49,182,029 stored bytes (payloads 49,071,543 bytes). All 36 manifests currently say `complete`. This is an inventory, **not** a saved SHA-256 baseline. Existing local `data/silver` and `data/gold` builds end at 2026-10-01, so their row counts below do not include the 2026-10-02 raw day. Daily raw manifests are operational mutable indexes while a day is incomplete; do not change old completed manifests for this migration.

| Leg | Existing payload count / shape | Source and coverage |
| --- | ---: | --- |
| `openrouter_models` | 36 `openrouter_models.json.gz` | `/api/v1/models`, one byte-exact JSON response with `data` array; full listed catalogue for that request. |

Older completed manifests omit legs introduced later. `load_or_empty` represents them in memory as `not_applicable`; a v2 reader must not reinterpret them as successful empty observations. Raw top/new lists are limited samples. HF provider list has 20-page/20,000-row safety limits, validates page shapes, and publishes no partial payload after a failed page. It still documents a filtered catalogue, not an independently verified complete inventory of every provider or every HF repository. A successful list pass alone cannot establish that an absent repository was delisted.

Other historical stores: `data/backfill/arxiv/<date_from>_<date_until>/<categories>/arxiv.jsonl.gz` plus `_manifest.json` (five successful range collections) were fetched on 2026-09-30 for earlier **OAI datestamp** windows. They are retrospective retrievals, not observations at those earlier dates. `data/enrichment/arxiv_ids/` holds 24 cached Atom XML response batches and a mutable resolution `_manifest.json`; `collector/arxiv_ids.py` owns it. Untracked local `data/spikes/replicate/2026-10-01/` holds bounded authenticated API spike responses and two manifests. `scripts/replicate_spike.py` is not a scheduled collector, and this sample cannot support population-wide deployment absence or longitudinal events. Do not sweep the spike into daily backfill without an explicit scope decision.

### Manifest and raw fields in use

Daily manifest top level: `schema_version`, `snapshot_date`, `collector_version`, `status`, `runs` (`started_at`, `finished_at`, `http_calls`), `legs`. Leg records vary: common `status`, `file`, `bytes_raw`, `bytes_stored`, `sha256_raw`; OpenRouter `url`, `http_status`, `fetched_at`, `attempts`; HF detail `requested`, `stored`, `permanent_failures`, `failures` (`hf_id`, `attempted_at`, `http_status`, `error`), `completed_at`, `source_file`; paginated legs `api`, `filter`/`sort` or `scope`, `pages`, `rows`, `target_rows`, `reached_target` or `mappings`, plus error/attempt fields for partial runs. Manifest `sha256_raw` hashes **decompressed logical payload bytes**, not the `.gz` file bytes.

Raw JSONL detail envelope: `hf_id`, `fetched_at`, `http_status`, `body`. HF list envelope: `page`, `url`, `fetched_at`, `http_status`, `body` array. HF provider envelope uses the same page fields; each body model has `id`, `inferenceProviderMapping`, and each mapping has observed `provider`, optional `providerId`, `task`, `status`, and potentially further fields preserved in raw. arXiv envelope has `category`, `page`, `url`, `fetched_at`, `http_status`, OAI header summary and base64 original XML. The OpenRouter payload itself contains source model `id`, `canonical_slug`, `hugging_face_id`, `created`, `context_length`, `pricing`, `architecture` and more unprojected fields. These are observed fields, not an exhaustive upstream API schema. Preserve unknown raw fields.

In the current saved Silver report: 241,378 HF raw observation rows, 237,930 selected HF repository/day rows, 15,326 OpenRouter model/day rows, 6,583 HF provider mapping rows on the first provider day, 25,800 unique HF repository IDs, and 504 unique OpenRouter IDs. Silver chooses one HF row per repository/day by detail > top > newest. `model_platform_links` collapses all daily OpenRouter `hugging_face_id` declarations to pairwise first/last seen spans, with `explicit_hugging_face_id` and `explicit_metadata`; it cannot represent a corrected mapping's belief history or gaps inside a span. `canonical_slug` resolves OpenRouter aliases, but is an **OpenRouter source field**, not an established cross-provider canonical model ID. HF repository, OpenRouter listing, underlying model family and deployment are currently different concepts that should not be merged implicitly. HF mapping `provider_name` *is* an inference provider, and `provider_model_id` is scoped to it. Multiple HF repos or mapping records may need conflict handling for the same provider ID.

## Timestamp semantics and confidence

| Existing field | Current meaning | V2 treatment |
| --- | --- | --- |
| Daily `snapshot_date` / directory | UTC logical collection day; only day precision. May contain legs fetched at different instants or resumed later. | Keep unchanged as day key. Never turn midnight into a claimed capture instant. |
| Envelope or OpenRouter manifest `fetched_at` | Collector capture time, usually second precision; best available `observed_at` for that response/row. | Preserve exact instant and original precision. For missing values use a documented day-granularity observation with precision marker, or quarantine if an instant is required. |
| Manifest run `started_at`, `finished_at`; leg `completed_at` | Collector execution bounds; not source effective dates and not always the individual payload capture time. | Fallback evidence only, with provenance and precision. Do not use migration time. |
| Source HF `createdAt`, `lastModified`; OpenRouter `created`; arXiv `submitted_at`, `updated_at`, `oai_datestamp` | Source-specific repository/listing/paper timestamps. OAI datestamp is metadata change time, not publication. | Populate `effective_at` only for the **matching claim** (e.g., repo-created event from HF `createdAt`), never for unrelated provider listing, pricing or delisting changes. |
| Silver `first_seen_date`, `first_seen_provider_date`, Gold `event_date` | First collector day, with source-vs-observation distinction only in v1 Gold events. | Keep v1 meaning. V2 uses response-level `observed_at`; first observed date is derived from it. |
| Retrospective arXiv backfill manifest `collected_at` | Actual 2026-09-30 retrieval time; date window is source OAI datestamp. | Observation is retrieval time, not the earlier date window. `is_backfill` describes replay/reconstruction, with separate provenance for retrospective source harvest. |

No current normalized row has a persisted `recorded_at`; old Silver/Gold build times cannot be recovered reliably. V2 materialization can record its actual UTC write time. `effective_at` stays null for unknown provider change timing. Store UTC instants as typed timestamp fields in v2, plus an `observed_precision`/`observed_basis` indicator when only a day is defensible. Do not silently equate source `created` with when a provider listed a deployment.

## Proposed additive v2 data model

Use new versioned derived files, for example `data/temporal_v2/`, leaving `data/raw`, v1 Silver and v1 Gold paths and schemas intact during parallel validation. Parquet is sufficient at present scale. The following are design contracts to confirm before coding:

| Dataset and grain | Proposed fields and constraints |
| --- | --- |
| `raw_snapshot_index` (one row per immutable payload) | `snapshot_id` (stable hash of archive-relative path + file SHA-256), `source`, `source_scope`, `snapshot_path`, `manifest_path`, `collection_day`, `collected_at`, `observed_basis`, `observed_precision`, `sha256_file`, `sha256_raw`, `size_bytes`, `collector_version`, `parser_version`, `schema_version`, `ingestion_run_id`, `run_status`, `leg_status`, `pagination_complete`, `absence_evidence_grade`. For historic files, fill only evidenced fields; nullable version/run IDs. Index manifests separately in baseline. |
| `canonical_models` (one internal identity) | `canonical_model_id` stable internal key, optional family/name metadata and creation provenance. Do not auto-promote `canonical_slug`, HF repo ID or a fuzzy match to universal identity. Unresolved deployments still exist. |
| `provider_deployments` (one provider and provider-local model ID) | `deployment_key`, `provider`, `provider_model_id` (source exact string), nullable `canonical_model_id`, `first_observed_at`, `last_observed_at`, `current_status`, `status_basis`. Unique `(provider, provider_model_id)` within a namespace. For HF mappings, `provider` is mapping `provider_name`; for OpenRouter listings it is `openrouter`. A missing/null provider ID needs a separate unresolved observation, not a fabricated deployment ID. |
| `deployment_observations` (one deployment per source snapshot) | `deployment_key`, `snapshot_id`, `source_scope`, `source_hf_repo_id`, `source_publisher`, `observed_at`, `observed_precision`, `recorded_at`, `is_backfill`, `presence_state` (`PRESENT`, `ABSENT_CONFIRMED`, `UNKNOWN`), `provider_status`, structured pricing, capabilities and context fields, source row locator/hash. Preserve source status like HF `live`, `staging`, `error` independently of presence. |
| `identity_links` (historical decision) | `link_id`, provider namespace and exact model ID, nullable `canonical_model_id`, nullable `hf_model_id`, `mapping_method` (`explicit_provider_mapping`, `exact_external_id`, `exact_slug`, `curated`, `fuzzy`, `unresolved`), `mapping_source`, `confidence`, source snapshot/row, `valid_from`, nullable `valid_to`, `observed_at`, `recorded_at`, `is_backfill`, decision version. Identity revisions append a new decision and close the old validity interval in a **derived history rebuild**, never by editing raw. Define half-open validity `[valid_from, valid_to)` and tie-breaking rules for simultaneous evidence. |
| `lifecycle_events` (one derived transition) | Deterministic `event_id`, `event_type`, `deployment_key`, nullable `canonical_model_id`, provider and source IDs, nullable `effective_at`, `observed_at`, `observed_precision`, `recorded_at`, `is_backfill`, source/previous snapshot IDs, structured `previous_value` and `new_value`, field path, mapping/provenance reference, algorithm version and evidence grade. Hash stable normalized inputs including event type, deployment, ordered snapshot identity and old/new typed-value hashes. Exclude `recorded_at` from ID. |

`MODEL_DISCOVERED` should be attached to an established canonical identity or explicitly marked provisional; `PROVIDER_LISTED` means first observed deployment presence, not launch date. `PROVIDER_ID_CHANGED` requires credible continuity evidence between old and new provider IDs; otherwise model two deployments plus a possible identity link. `HF_IDENTITY_LINKED/REVISED` are decisions with recorded evidence, not mere string resemblance. Compare normalized, typed values for price, context and capability changes; retain original units and raw values. No random event IDs or destructive in-place event migration.

### Absence and delisting gate

Only a successful, scope-matching and demonstrably complete catalogue can support absence. Gate on manifest day/leg `ok`, payload integrity, expected endpoint/filter, all cursor pages, no bound hit, no error/rate limit, and anomaly checks on catalogue counts. Record `UNKNOWN` for missing files, partial runs, `not_applicable` legs, unrelated or bounded HF top/new samples, and provider-filtered disappearance whose filter semantics do not prove removal. For HF inference mappings, a repository disappearing from the entire provider-filtered list remains `UNKNOWN`; disappearance of one mapping while the **same repository remains explicitly returned** with a complete mapping array is a candidate confirmed absence, subject to checking endpoint guarantees and (if unstable) repeated successful observations. For OpenRouter, a model absent from an otherwise complete catalogue could be `ABSENT_CONFIRMED` only after source-specific coverage checks and an agreed consecutive-run threshold. Emit `PROVIDER_DELISTED` only on `PRESENT -> ABSENT_CONFIRMED`; emit `MODEL_REAPPEARED` after such a confirmed absence. A later present row after `UNKNOWN` does not prove reappearance.

## Migration impact, hazards and change sequence

1. **Freeze an archive baseline before implementation.** Read all existing `data/raw/**` files, including manifests, and also decide whether backfill/enrichment/spike payloads enter the protected set. Write a *new* `historical_archive_baseline.json` outside `data/raw` with UTC generation time, file count, total bytes, min/max archive collection day, and per archive-relative path byte length + SHA-256 of the stored file bytes. Treat it as a dated baseline, never overwrite it. Re-run verification after each phase and after backfill; any pre-existing path missing or hash changed is a hard stop. New daily snapshots may legitimately increase the archive, so compare the frozen path set, not total counts alone. Keep the manifest's `sha256_raw` as a second, different integrity check.
2. Add synthetic tests for v1 behavior and frozen-path byte preservation. Do not run `python -m collector` on a historical day: the CLI accepts `--date`, and an unfinished old day could be resumed with today's API responses. Keep the daily scheduler unchanged while v2 develops.
3. Build the new raw index from read-only files. Establish timestamp/source scope and `PRESENT/UNKNOWN` quality rules; do not inject metadata into old payloads or rewrite old manifests. Pin a parser version and record any undecidable historical metadata as null with a reason.
4. Implement separate temporal observation and deployment outputs, then identity decision history. Test explicit mappings outrank fuzzy candidates, ambiguous matches remain unresolved, and corrections preserve prior belief intervals. Confirm the canonical identity policy with real collision cases before assigning cross-provider IDs.
5. Derive deterministic events from chronologically ordered observations. Test identical snapshots, one price transition, failed/partial snapshot, confirmed absence, and reappearance with tiny synthetic histories. A first historical snapshot is left-censored: first observed presence, not proved first listing.
6. Add a `python -m ... backfill --from ... --to ... --dry-run` style command after interface review. Dry-run must write no derived files; live mode writes only new v2 paths using atomic output and restartable/idempotent partition or rebuild semantics. Historical `observed_at` comes from capture evidence, `recorded_at` from this execution, `is_backfill=true`, and unknown `effective_at=NULL`.
7. Store a validation report before consumer cutover: frozen-path hash equality, counts/bytes, provider-specific earliest/latest capture time, snapshots, successful runs and model observations; v1/v2 deployment and HF-link coverage and unresolved identities with explained differences; event counts by type and day/provider, especially delisting spikes. Run existing `pytest -q`, `ruff check .`, and v2 tests after each implementation stage. Retain v1 Silver/Gold rebuilds and compare in parallel. Add compatibility views only if a consumer needs them; downstream research marts follow validated v2 semantics.

### Operations that could modify historical or existing outputs

| Operation | Risk / rule |
| --- | --- |
| `collector.run.collect` on a partial historical day; `Context.store`; `manifest.save` | Can atomically replace a payload and manifest while resuming. Never invoke against a protected historical day during migration; use isolated test roots. Completed days currently short-circuit. |
| `collector.arxiv_backfill` on a failed prior range | Could replace a range payload/manifest; exclude it from lifecycle replay execution and baseline-protect it. Successful prior range is refused by current code. |
| `collector.arxiv_ids.resolve` | Mutates its enrichment manifest while resolving new IDs; leave it alone during baseline checks or account for new entries. |
| `scripts/replicate_spike.py` | Writes sample files/manifests under `data/spikes`, currently untracked; not part of the scheduled catalogue. |
| `python -m silver`; `python -m gold` | Rewrite `data/silver/*` and `data/gold/*` by design. They do not rewrite Bronze, but would change local derived outputs and may currently incorporate the extra 2026-10-02 day. Run only after recording comparison baselines or in an isolated output path. |
| Git workflow commit/pull; `scripts/pull_snapshots.ps1` | Adds/pulls new raw history and may update the local checkout; use frozen-path hash comparison to distinguish additions from changes. Never rewrite Git history or completed snapshots. |

### Existing consumers and tests affected

`silver/build.py` assumes exact raw file names, manifest leg `ok`, fixed v1 schemas, OpenRouter prefix-based `provider`, and date-level first seen. `gold/build.py` assumes HF repo identity, `model_platform_links` collapsed spans, old event labels and day dates. `collector/audit.py` relies on manifest `sha256_raw` and day/leg status; `collector/arxiv_ids.py` reads Silver tags; `scripts/pull_snapshots.ps1` and the collect workflow assume the current raw layout. README, `docs/gold_metric_contract.md`, findings and ADR explain v1 meanings and will need additive v2 documentation rather than silent reinterpretation. Tests covering the existing contract are `test_bronze_is_verbatim.py`, `test_idempotence.py`, `test_resume.py`, `test_audit.py`, `test_hf_top_models.py`, `test_hf_new_models.py`, `test_hf_inference_providers.py`, `test_arxiv.py`, `test_arxiv_ids.py`, `test_silver.py`, and `test_gold.py`. None currently proves a frozen real archive's per-file stored-byte hashes survive a v2 migration, or tests provider lifecycle transitions and identity correction history.

## Accepted decisions and boundaries for Phase 2

The accepted identity policy is `HF repository -> identity link -> optional canonical_model`: an HF repository is not automatically a canonical model, and `canonical_model_id` can be null. Later family/variant modeling must preserve deployment history. The protected baseline includes every existing file, including manifests, under `data/raw`, `data/backfill/arxiv` and `data/enrichment/arxiv_ids`. `data/spikes/replicate` remains outside production lifecycle history and this index. OpenRouter and HF provider mapping absence require separate, explicitly reviewed completeness rules. Until those rules are formalized, no observation can generate a real `PROVIDER_DELISTED`. Phase 2 implements no lifecycle event generation or canonical assignment.

The original baseline stays permanent forensic evidence; an active baseline is a separate dated fingerprint with an explicit append-only activation record after a reviewed legitimate enrichment manifest update. The next layer follows `raw_snapshot_index -> deployment_observations -> provider_deployments`, retaining exact provider IDs, page-level observed times, null unknown effective dates, source pricing/context/capabilities and evidence. It performs no identity resolution and generates no lifecycle events. Missing evidence remains unknown; positive source mapping/listing observations do not imply healthy inference service.
